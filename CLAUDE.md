# YourHarness

Native macOS (26+, Apple Silicon only) harness over AI coding CLIs. SwiftUI app plus the `HarnessCore` library. See README.md for the architecture.

## Build

`xcode-select` on this machine may point at the Command Line Tools, which can't build. Always prefix:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
swift build
swift test
scripts/bundle.sh   # → build/YourHarness.app
```

## Versions and releases

The user's main app is `/Applications/YourHarness.app`, installed by releases; `build/YourHarness.app` is the development build. The version is in `VERSION` (semver, from 0.0.1). When a feature lands, add a line to CHANGELOG.md under **Unreleased**, in the reader's terms. `scripts/release.sh <version>` cuts a release (changelog, tag, push, install); the tag's workflow publishes the DMG on GitHub Releases. It needs a clean tree: stash only the user's own uncommitted files, by name, around it, and put them back.

Builds are signed with the app's own self-signed certificate, "YourHarness Self-Signed", so macOS sees every build as the same app and keeps the permissions it was given, and the updater only installs updates signed the same way. The certificate and its passwords live in `~/.yourharness/signing` (back it up: a lost certificate means a new identity, and macOS asking for everything again) and in the repo's `SIGNING_P12` / `SIGNING_P12_PASSWORD` secrets for the release workflow. `scripts/bundle.sh` signs with it when it's there, in a keychain of its own (`scripts/signing-keychain.sh`), never the login keychain, so signing never prompts; without it, ad hoc. Dev copies (`scripts/dev-app.sh`) are always ad hoc.

Integration tests spawn the real `claude` CLI on Haiku and the real `git`/`gh`: `YH_INTEGRATION=1 swift test --filter Integration`.

For manual runs, use a Dev copy (`scripts/dev-app.sh <dir>` makes `YourHarness Dev.app` with its own bundle ID, so it never shares permissions, notifications or browser data with the user's app), point it at a throwaway state so it never scans the user's real projects, pass your PATH so it doesn't start the user's login shell (their `.zshrc` reads from `~/Downloads`, and macOS asks them for access on behalf of every new build), and launch it in the background so it never takes focus from what the user is typing: `open -g -n --env YH_DATA_DIR=<scratch dir> --env YH_PATH="$PATH" "<dir>/YourHarness Dev.app"` (one `--env` per variable). Running the executable directly brings the window to the front. A test run must never put a macOS privacy prompt in front of the user. Set it up with a `state.json` that lists only folders you're allowed to touch: it seeds an empty data folder, and once the app has run, state lives in `harness.sqlite` (see docs/storage.md; delete it to seed again). `scripts/preset.sh <preset>` makes such a folder in `test-harness-root/` from `presets/` (`legacy-0.0.6`: data as 0.0.6 saved it, for testing the upgrade; `legacy-big`: generated history at scale; `sandbox-prs`: a clone of github.com/mdovhopo/yourharness-test-prs, where test runs may push and open PRs, on Haiku), and `scripts/dev-run.sh <folder> [YH_VAR=value …]` launches a Dev copy on it the safe way, logging to `<folder>/dev.log`, and `scripts/dev-quit.sh <folder>` quits that copy (never quit Dev copies by name: other sessions run theirs). Use Haiku for real Claude turns in tests. Add `YH_SIMULATE_STREAMING=1` to stream the markdown sample (`StressTest.markdownSample`) into the selected thread at launch, for checking rendering and streaming without clicking. `YH_OPEN_DIAGRAM=<file.mmd>` opens a Mermaid file in the large diagram window. `YH_SEND_MESSAGE=<text>` (plus optional `YH_SEND_FILES=<a.png:b.pdf:folder>`, images inline and the rest by path; `YH_SEND_IMAGES` still works) sends a message from a new thread at launch (a real Claude turn plus title generation), so keep the state's folders throwaway; with `YH_SEND_IN_SELECTED=1` it goes to the selected thread instead, continuing its session (for a second message: launch, quit, launch again). `YH_SEND_FILES` alone attaches them to the selected thread's composer instead, as a drop does. `YH_DRAFT=<text>` (`\n` for new lines) puts a draft in the selected thread's composer, unsent, the cursor at its end as after typing (`YH_DRAFT_CURSOR=start` at the top), for checking how a long draft scrolls; `YH_DRAFT=/co` opens the slash command menu. `YH_RESUME_SESSION=<session id>` opens the Resume Claude Code Session sheet filled in, and `YH_RESUME_CONFIRM=1` then resumes it into the suggested project. `YH_NOTIFICATIONS=log` prints notifications and the Dock badge to stderr instead of posting them, so a test instance never asks for notification permission (it would prompt the user, and the bundle ID is shared with their app). `YH_BROWSER_PROBE=<steps.json>` runs browser tool calls (`[{"tool": "click", "args": {"selector": "#go"}}, {"sleep": 1}]`) on the selected thread at launch and prints each result to stderr, screenshots next to the file: for testing the browser tools exactly, and for checking snapshots on real sites, without a model. After changing anything in `Browser/` or the browser panel, run `scripts/browser-fidelity/run.sh` (about a minute; `SKIP_BUILD=1` to reuse `build/`): it renders test pages in a plain, unscaled WebKit view (Safari's engine) at every page size and checks the built-in browser against it, what the page measures and how the screenshots look, in the side panel, parked and in its own window, and checks its input against a real mouse (hover, exact clicks, pointer drags, HTML drag and drop, scrolling). The browser is how Claude sees the UI it builds, so this must pass. A development run never uses your real home folder: if its state doesn't load, it says why on stderr and Home is a `home` folder inside the data dir (running `claude` in your home folder sets off macOS's folder-access prompts). `YH_THREADS_PROBE=<steps.json>` runs the thread tools at launch (`[{"as": "<thread id>", "tool": "list_threads", "args": {}}]`, `as` picks the calling thread, whose project decides what it reaches) and prints each result and the selection at the end to stderr; pass `CLAUDE_CONFIG_DIR=<scratch>` for the Claude Code sessions, never your real `~/.claude`. `YH_STATE_EXPORT=<file.yhstate>` exports the whole state at launch (`YH_STATE_EXPORT_SIGNINS=1` with the browser's cookies) and prints its manifest to stderr; `YH_STATE_IMPORT=<file.yhstate>` imports one at launch without asking, scratch states only (Home is pointed at the scratch `home` folder; other projects keep the file's paths, so only import files whose project folders are throwaway or missing); `YH_STATE_IMPORT_ASK=<file>` opens Import State's question for it (snapshot it with `YH_SNAPSHOT`), and `YH_STATE_IMPORT_CONFIRM=1` then says yes, keeping a copy, and restarts (without the `YH_STATE_*` variables). To reproduce someone's bug, `scripts/preset.sh` any preset, then `scripts/dev-run.sh <folder> YH_STATE_IMPORT=<their file>`; never import into your real app to look at someone else's state. Dev copies share one browser profile, so an import with sign-ins resets the browser of the file's projects for every Dev copy. `YH_IMPORT_COOKIES=<Cookies.binarycookies>` imports a Safari-format cookie file into the selected thread's project at launch: test cookie import with a synthetic file, never by reading the user's real Safari or Chrome (that prompts them for Full Disk Access or the keychain). `YH_MOCK_PULLS=<pulls.json>` serves pull requests from a file instead of `gh`/`glab` (see `Support/MockPullRequests.swift` for the shape), for a scratch workspace whose remotes point at a forge it can't reach; the file is read again when it changes, so editing it mid-run (a PR merged, one gone from the open list) shows up at the next refresh. `YH_PR_PANEL_LOG=1` prints every change in what the right sidebar's PRs tab lists (which PRs, in what order and state), for telling a flicker. `YH_UPDATE_FEED=<release.json>` reads releases from a file shaped like GitHub's `releases/latest`, or a `releases` list for several releases' notes, instead of GitHub (its disk image may be a `file://` or local `http://` URL): Dev copies only look for updates with it, and an update only installs over an app with the same bundle ID, so test the whole flow (download, Restart) with a Dev copy and a DMG of a Dev copy with a higher version. Restart reopens with the same `YH_*` variables, in the background when `YH_DATA_DIR` is set. `YH_SWITCH_PROBE=<rounds>` switches through the sidebar's threads that many rounds at launch, as clicking does, and prints to stderr each switch as it happens and a summary: go by **main thread busy** (CPU time), not wall time, which a background window inflates (it's drawn late). `YH_SWITCH_ANIMATED=0` switches without the sidebar's animation, `YH_SWITCH_PROBE_THREADS=<n>` goes round the first n threads only (visited ones stay made, see `TranscriptDeck`, so that's the back-and-forth case), `YH_KEPT_TRANSCRIPTS=<n>` changes how many stay made, `YH_TURNS_PER_PAGE=<n>` changes how many turns a transcript lists. Run it on a big scratch state after changes to the thread view, and on one whose threads end in big Mermaid diagrams after changes to diagrams (they cost on every switch: make one by appending replies with three ```` ```mermaid ```` blocks of 25–40 nodes to `legacy-big`'s long threads). A row counts as in view when any part of it is, since a diagram or a long answer can be taller than the screen. For the transcript going blank: after each switch it checks for rows but none in view, a window of the app's over the main one, and nothing drawn in the conversation area (`BLANK` lines); `YH_SWITCH_PROBE_SCROLL=<points>` reads back that far in each thread before leaving (real wheel events), `YH_SWITCH_PROBE_HOLD=<ms>` stays put after each check, `YH_SWITCH_PROBE_SHOTS=<folder>` keeps drawings of the first blanks, `YH_BLANK_WATCH=1` checks the open thread four times a second the whole run (`YH_BLANK_SCROLL=<seconds>` scrolls it up once then, as reading back mid-turn does), and `YH_FULL_SCREEN=1` makes the window full screen at launch. Debug → Capture Transcript State (`YH_CAPTURE_TRANSCRIPT=<seconds>` at launch) writes the open transcript's scroll position, rows in view and window state to `diagnostics/` in the data folder. Never run `screencapture` from a test: it puts a privacy dialog on the screen even when `CGPreflightScreenCaptureAccess()` says it's allowed; use the app's own drawing (`YH_SNAPSHOT`, `YH_PERF_SHOTS=1`), which can't show glass. `scripts/perf-run.sh <results folder>` is the heavy run: a Dev copy on the `extreme` preset with a fake `claude` streaming up to 20 huge threads at once through the app's real path, recording FPS, frames missed, stalls, CPU and memory to `phases.json` and `seconds.csv`, and how long clicks take (switching threads, expanding work, the inspector, the project page, a new thread) to `clicks.json` (`YH_PERF_PHASES=stream-all,settled`, `YH_PERF_SECONDS=<n>`, `YH_PERF_WAIT=<seconds>` to attach Time Profiler; plugged in only). Compare builds with `YH_APP_DIR=<folder with a Dev copy>`; go by the `PERF stall` lines for freezes, and see docs/performance.md for the results so far and what they don't show yet. `YH_PERF_FRONT=1` is the true test and takes over the Mac: full screen, floating above everything, the real pointer moving over the transcript; without it the window sits below the screen with no real pointer, and hover-driven freezes don't show. A run prints `INVALID` when the window couldn't be seen (the display off, the screen locked, another Space): frames stop with the main thread idle and clicks seem to take seconds, which says nothing about the app; only trust a run without those lines. `YH_PERF_PHASES=stream-all-everything` times every kind of interaction (typing, tabs, search, find, jumps, sidebar actions, pages, live resizing, `YH_PERF_ONLY=<groups>` for some), `stream-all-chaos` does anything in any order (`YH_PERF_CHAOS_SEED=<n>` plays a run again, each action is logged first so a crash says what led to it), `PERF_SEED=<dir>` runs on a smaller seed, and `YH_ROW_CHECK=1` fails when a row's height in the list isn't what SwiftUI makes of it. Keep hover animation off whole rows: animate only what fades, and never let hovering change a row's height. `YH_NAV_PROBE=<folder>` goes between threads, a new thread, a project's Pull Requests and Memory pages and the right sidebar, wide and at the narrowest, through the sidebar's own calls, drawing the window after each step into the folder and printing PASS/FAIL: a step fails if it makes the window bigger (Memory once grew it to 4000 pt tall, and 1300 wide with memories in it: try it on `scripts/preset.sh memory` with `YH_MEMORY_SEED=200` too) or the right sidebar doesn't give back the width it took. Run it after changes to the window's layout or a page's. ## Principles

- **Performance and memory are the product.** Check app footprint (`footprint $(pgrep -x YourHarness)`) after UI changes that touch the transcript. Use Debug → stress transcript. The transcript is a list in AppKit (`TranscriptListView`, each row's content a small SwiftUI view in its own hosting view; `TranscriptDeck` keeps each thread's made and parks it): don't go back to a lazy stack with a scroll position, or put what changes often in the window's own hosting view, which froze and crashed the app. See docs/performance.md.
- **Apple-quality UI.** Native controls, Liquid Glass (`glassEffect`, `.glass` button styles), SF Symbols, standard shortcuts. No web views. Draw from `Views/Theme.swift` so the window stays coherent: content sits on the `.canvas` (set once under the detail column), boxes use `.card()`, labels use `Chip`, radii come from `Theme`. Glass is for what floats above content (composer, prompts, buttons), not for transcript rows.
- **`HarnessCore` never imports SwiftUI/AppKit.** Adapters emit `AgentEvent`. The UI only consumes `AgentEvent`.
- **CLI protocols change often.** Parsers ignore unknown event types and must never crash on new fields. When the protocol changes, capture a real session, sanitize it (no local paths or user config), and add it under `Tests/HarnessCoreTests/Fixtures/`.
- **Never extract or reuse CLI credentials.** Always drive the official binary.

## Keeping it fast

Each of these comes from a freeze, a crash or a day lost; docs/performance.md has the evidence.

**Where code goes.** Anything big, long-lived or updating many times a second goes in AppKit. What you open now and then stays in SwiftUI (Settings, Usage, Memory, pull request pages, popovers, sheets). Move more over because a measurement says so, not by default.

- **Nothing that changes often in the window's hosting view.** A change there goes through the whole window's graph, toolbar included. Give it a hosting view of its own, as transcript rows have.
- **No lazy stack with a scroll position for anything that streams.** Its heights are estimates and moving your place changes what it measures next, so it can go back and forth for good, inside SwiftUI's update, where nothing can stop it.
- **`.toolbar` where it isn't re-evaluated.** In a body that updates often, it rebuilds its items and asks for another layout pass, which is how a loop in the transcript became a crash. Put it in a `ViewModifier` with only values that rarely change (`SelectedThreadToolbar`, `InspectorToolbar`). Likewise `RootView` must not read the selection, or every switch goes through the split view and all its columns (`DetailColumn`, `InspectorColumn`).
- **Watch only what you use.** Reading `thread.entries` updates a view for every new row: `hasNoEntries` says what most views want. What's hidden makes nothing (the right sidebar built its panels on every switch while closed).
- **`@Observable`, tested on Swift 6.4:** assigning an equal value tells nobody, `didSet` or not, so don't guard writes. In-place changes (`append`, `+=`) always tell, and so does any assignment of a type that isn't `Equatable`.
- **Answer the click, then do the work.** The first frame shows the selection and the title; what's slow follows a run loop pass later (`TranscriptDeckView.show`, `InspectorColumn`). Time both: `PerfProbe` logs when a click was answered and when it was done.
- **Nothing long on the main thread from a click or an event.** Histories load with `loadTranscriptSoon`, never `loadTranscriptIfNeeded`. Long tool output is looked through aside (`noteLinks`). Going through tens of thousands of rows yields now and then (`transcriptForReading`).
- **Animate what fades, not rows.** Never start an animation from something that fires as content moves: `easeOut` can't merge, and SwiftUI stacks them until a frame takes minutes. Hovering never changes a row's height. What spins or pulses is Core Animation (`SpinningClaudeMark`, `pulsing`): a repeating SwiftUI animation or a `TimelineView` lays the window out on every frame.
- **SwiftUI inside AppKit.** A row's hosting view has `safeAreaRegions = []`, or scrolled under the toolbar it's pushed down inside itself. In the detail column, `.ignoresSafeArea()` on all edges reaches under the sidebars: use `edges: .vertical`. A SwiftUI `ScrollView` in a row keeps wheel events it can't use, hence `TranscriptWheelRouter`. A wheel event moves the scroll view after `scrollWheel` returns, so don't judge where it went until later.

## Testing performance

- **First check the run is valid.** A window that can't be seen (display off, screen locked, another Space) gets few frames with the main thread idle, and clicks seem to take seconds. A day went to explaining "830 ms clicks" that were this, with `windowVisible: false` in `phases.json` all along. Trust no run with `INVALID` lines. `pmset -g log | grep "Display is turned"` shows the display going off; `lsappinfo front` says `loginwindow` when the screen is locked, and this Mac locks after about 20 idle minutes whatever `caffeinate` does, so check long runs at the end too.
- **Look at the sequence, not the median.** `clicks.csv` and `seconds.csv` over time: frames gone with the main thread idle isn't the app, and a sudden step in click times isn't load building up. Medians hid both.
- **Compare before believing.** A slowdown counts once a baseline build (`YH_APP_DIR`) doesn't show it under the same conditions; a fix counts once the same test fails without it, over several runs, as a freeze can be one run in three.
- **Two failed patches on one mechanism: question the mechanism.** Telling the lazy stack to go to an edge, a row, a point each just changed how it froze (the point froze for good). Replacing it took less time than the patches had.
- **Test what you assume about a framework** with a small program before building on it or writing it down. Guards against same-value `@Observable` writes shipped with a comment explaining them, and a 30-second test showed they did nothing.
- **Widen the test before trusting it.** The crash only showed once the probe went beyond six kinds of click. Add new user actions to `everything` and `chaos` in `PerfProbe`, and run `stream-all-chaos` on the full preset before a release.
- **Probes take the real path.** A wheel event handed straight to the list hid the code block that would have swallowed it. Go through what a real event goes through, or say in the probe what it skips.
- **Numbers don't see layout.** Rows clipped under about 876 pt with every check passing. After layout changes, look at what `YH_NAV_PROBE` draws at narrow widths and with the right sidebar open.
- **A frozen run never exits.** `perf-run.sh` has no time limit: run long ones in the background and watch for `PERF freeze` lines. `YH_PERF_SECONDS` applies to every phase, `settled` included. Dev copies share a saved window frame: `perf-run.sh` clears it, other runs don't, so `defaults delete com.mdovhopo.yourharness.dev "NSWindow Frame main"` before comparing layouts.
