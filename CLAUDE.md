# YourHarness

Native macOS (26+, Apple Silicon only) harness over AI coding CLIs. SwiftUI app plus the `HarnessCore` library. See README.md for the architecture.

## Build

`xcode-select` on this machine may point at the Command Line Tools, which can't build. Always prefix:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
swift build
swift test
scripts/bundle.sh   # → build/YourHarness.app
```

## Versions and releases

The user's main app is `/Applications/YourHarness.app`, installed by releases; `build/YourHarness.app` is the development build. The version is in `VERSION` (semver, from 0.0.1). When a feature lands, add a line to CHANGELOG.md under **Unreleased**, in the reader's terms. `scripts/release.sh <version>` cuts a release (changelog, tag, push, install); the tag's workflow publishes the DMG on GitHub Releases.

Builds are signed with the app's own self-signed certificate, "YourHarness Self-Signed", so macOS sees every build as the same app and keeps the permissions it was given, and the updater only installs updates signed the same way. The certificate and its passwords live in `~/.yourharness/signing` (back it up: a lost certificate means a new identity, and macOS asking for everything again) and in the repo's `SIGNING_P12` / `SIGNING_P12_PASSWORD` secrets for the release workflow. `scripts/bundle.sh` signs with it when it's there, in a keychain of its own (`scripts/signing-keychain.sh`), never the login keychain, so signing never prompts; without it, ad hoc. Dev copies (`scripts/dev-app.sh`) are always ad hoc.

Integration tests spawn the real `claude` CLI on Haiku and the real `git`/`gh`: `YH_INTEGRATION=1 swift test --filter Integration`.

For manual runs, use a Dev copy (`scripts/dev-app.sh <dir>` makes `YourHarness Dev.app` with its own bundle ID, so it never shares permissions, notifications or browser data with the user's app), point it at a throwaway state so it never scans the user's real projects, pass your PATH so it doesn't start the user's login shell (their `.zshrc` reads from `~/Downloads`, and macOS asks them for access on behalf of every new build), and launch it in the background so it never takes focus from what the user is typing: `open -g -n --env YH_DATA_DIR=<scratch dir> --env YH_PATH="$PATH" "<dir>/YourHarness Dev.app"` (one `--env` per variable). Running the executable directly brings the window to the front. A test run must never put a macOS privacy prompt in front of the user. Set it up with a `state.json` that lists only folders you're allowed to touch. Add `YH_SIMULATE_STREAMING=1` to stream the markdown sample (`StressTest.markdownSample`) into the selected thread at launch, for checking rendering and streaming without clicking. `YH_OPEN_DIAGRAM=<file.mmd>` opens a Mermaid file in the large diagram window. `YH_SEND_MESSAGE=<text>` (plus optional `YH_SEND_IMAGES=<a.png:b.png>`) sends a message from a new thread at launch (a real Claude turn plus title generation), so keep the state's folders throwaway. `YH_SEND_IMAGES` alone attaches the images to the selected thread's composer instead, as a drop does. `YH_RESUME_SESSION=<session id>` opens the Resume Claude Code Session sheet filled in. `YH_NOTIFICATIONS=log` prints notifications and the Dock badge to stderr instead of posting them, so a test instance never asks for notification permission (it would prompt the user, and the bundle ID is shared with their app). `YH_BROWSER_PROBE=<steps.json>` runs browser tool calls (`[{"tool": "click", "args": {"selector": "#go"}}, {"sleep": 1}]`) on the selected thread at launch and prints each result to stderr, screenshots next to the file: for testing the browser tools exactly, and for checking snapshots on real sites, without a model. A development run never uses your real home folder: if its state doesn't load, it says why on stderr and Home is a `home` folder inside the data dir (running `claude` in your home folder sets off macOS's folder-access prompts). `YH_IMPORT_COOKIES=<Cookies.binarycookies>` imports a Safari-format cookie file into the selected thread's project at launch: test cookie import with a synthetic file, never by reading the user's real Safari or Chrome (that prompts them for Full Disk Access or the keychain). `YH_MOCK_PULLS=<pulls.json>` serves pull requests from a file instead of `gh`/`glab` (see `Support/MockPullRequests.swift` for the shape), for a scratch workspace whose remotes point at a forge it can't reach. `YH_UPDATE_FEED=<release.json>` reads releases from a file shaped like GitHub's `releases/latest`, or a `releases` list for several releases' notes, instead of GitHub (its disk image may be a `file://` or local `http://` URL): Dev copies only look for updates with it, and an update only installs over an app with the same bundle ID, so test the whole flow (download, Restart) with a Dev copy and a DMG of a Dev copy with a higher version. Restart reopens with the same `YH_*` variables, in the background when `YH_DATA_DIR` is set. `YH_SWITCH_PROBE=<rounds>` switches through the sidebar's threads that many rounds at launch, as clicking does, and prints to stderr how long each switch took until the thread was on screen and the main thread free again (`YH_SWITCH_ANIMATED=0` without the sidebar's animation): run it on a big scratch state after changes to the thread view, and don't run `sample` at the same time, it slows the process several times over. `YH_OPEN_BROWSER_WINDOW=1` opens the selected thread's browser in its own window. `YH_APPEARANCE=light|dark` overrides the Appearance setting without saving it. `YH_OPEN_SETTINGS=1` opens Settings. `YH_SCROLL_PROBE=<points>` scrolls the open thread up (negative: down) in trackpad-sized steps and prints how often a row on screen moved by more or less than the step, the jump count; `YH_SCROLL_PROBE=log` prints the scroll geometry instead. Run it after transcript layout changes. The right sidebar's open state is saved (`showsInspector` in `state.json`), so a scratch state can open it.

## Principles

- **Performance and memory are the product.** Check app footprint (`footprint $(pgrep -x YourHarness)`) after UI changes that touch the transcript. Use Debug → stress transcript.
- **Apple-quality UI.** Native controls, Liquid Glass (`glassEffect`, `.glass` button styles), SF Symbols, standard shortcuts. No web views. Draw from `Views/Theme.swift` so the window stays coherent: content sits on the `.canvas` (set once under the detail column), boxes use `.card()`, labels use `Chip`, radii come from `Theme`. Glass is for what floats above content (composer, prompts, buttons), not for transcript rows.
- **`HarnessCore` never imports SwiftUI/AppKit.** Adapters emit `AgentEvent`. The UI only consumes `AgentEvent`.
- **CLI protocols change often.** Parsers ignore unknown event types and must never crash on new fields. When the protocol changes, capture a real session, sanitize it (no local paths or user config), and add it under `Tests/HarnessCoreTests/Fixtures/`.
- **Never extract or reuse CLI credentials.** Always drive the official binary.
