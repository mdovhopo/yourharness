# YourHarness

Native macOS (26+, Apple Silicon only) harness over AI coding CLIs. SwiftUI app plus the `HarnessCore` library. See README.md for the architecture.

## Build

`xcode-select` on this machine may point at the Command Line Tools, which can't build. Always prefix:

```sh
export DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer
swift build
swift test
scripts/bundle.sh   # → build/YourHarness.app
```

## Versions and releases

The user's main app is `/Applications/YourHarness.app`, installed by releases; `build/YourHarness.app` is the development build. The version is in `VERSION` (semver, from 0.0.1). When a feature lands, add a line to CHANGELOG.md under **Unreleased**, in the reader's terms. `scripts/release.sh <version>` cuts a release (changelog, tag, push, install); the tag's workflow publishes the DMG on GitHub Releases.

Builds are signed with the app's own self-signed certificate, "YourHarness Self-Signed", so macOS sees every build as the same app and keeps the permissions it was given, and the updater only installs updates signed the same way. The certificate and its passwords live in `~/.yourharness/signing` (back it up: a lost certificate means a new identity, and macOS asking for everything again) and in the repo's `SIGNING_P12` / `SIGNING_P12_PASSWORD` secrets for the release workflow. `scripts/bundle.sh` signs with it when it's there, in a keychain of its own (`scripts/signing-keychain.sh`), never the login keychain, so signing never prompts; without it, ad hoc. Dev copies (`scripts/dev-app.sh`) are always ad hoc.

Integration tests spawn the real `claude` CLI on Haiku and the real `git`/`gh`: `YH_INTEGRATION=1 swift test --filter Integration`.

For manual runs, use a Dev copy (`scripts/dev-app.sh <dir>` makes `YourHarness Dev.app` with its own bundle ID, so it never shares permissions, notifications or browser data with the user's app), point it at a throwaway state so it never scans the user's real projects, pass your PATH so it doesn't start the user's login shell (their `.zshrc` reads from `~/Downloads`, and macOS asks them for access on behalf of every new build), and launch it in the background so it never takes focus from what the user is typing: `open -g -n --env YH_DATA_DIR=<scratch dir> --env YH_PATH="$PATH" "<dir>/YourHarness Dev.app"` (one `--env` per variable). Running the executable directly brings the window to the front. A test run must never put a macOS privacy prompt in front of the user. Set it up with a `state.json` that lists only folders you're allowed to touch: it seeds an empty data folder, and once the app has run, state lives in `harness.sqlite` (see docs/storage.md; delete it to seed again). `scripts/preset.sh <preset>` makes such a folder in `test-harness-root/` from `presets/` (`legacy-0.0.6`: data as 0.0.6 saved it, for testing the upgrade; `legacy-big`: generated history at scale; `sandbox-prs`: a clone of github.com/mdovhopo/yourharness-test-prs, where test runs may push and open PRs, on Haiku), and `scripts/dev-run.sh <folder> [YH_VAR=value …]` launches a Dev copy on it the safe way, logging to `<folder>/dev.log`, and `scripts/dev-quit.sh <folder>` quits that copy (never quit Dev copies by name: other sessions run theirs). Use Haiku for real Claude turns in tests. Add `YH_SIMULATE_STREAMING=1` to stream the markdown sample (`StressTest.markdownSample`) into the selected thread at launch, for checking rendering and streaming without clicking. `YH_OPEN_DIAGRAM=<file.mmd>` opens a Mermaid file in the large diagram window. `YH_SEND_MESSAGE=<text>` (plus optional `YH_SEND_IMAGES=<a.png:b.png>`) sends a message from a new thread at launch (a real Claude turn plus title generation), so keep the state's folders throwaway; with `YH_SEND_IN_SELECTED=1` it goes to the selected thread instead, continuing its session (for a second message: launch, quit, launch again). `YH_SEND_IMAGES` alone attaches the images to the selected thread's composer instead, as a drop does. `YH_DRAFT=<text>` (`\n` for new lines) puts a draft in the selected thread's composer, unsent, the cursor at its end as after typing (`YH_DRAFT_CURSOR=start` at the top), for checking how a long draft scrolls; `YH_DRAFT=/co` opens the slash command menu. `YH_RESUME_SESSION=<session id>` opens the Resume Claude Code Session sheet filled in, and `YH_RESUME_CONFIRM=1` then resumes it into the suggested project. `YH_NOTIFICATIONS=log` prints notifications and the Dock badge to stderr instead of posting them, so a test instance never asks for notification permission (it would prompt the user, and the bundle ID is shared with their app). `YH_BROWSER_PROBE=<steps.json>` runs browser tool calls (`[{"tool": "click", "args": {"selector": "#go"}}, {"sleep": 1}]`) on the selected thread at launch and prints each result to stderr, screenshots next to the file: for testing the browser tools exactly, and for checking snapshots on real sites, without a model. After changing anything in `Browser/` or the browser panel, run `scripts/browser-fidelity/run.sh` (about a minute; `SKIP_BUILD=1` to reuse `build/`): it renders test pages in a plain, unscaled WebKit view (Safari's engine) at every page size and checks the built-in browser against it, what the page measures and how the screenshots look, in the side panel, parked and in its own window, and checks its input against a real mouse (hover, exact clicks, pointer drags, HTML drag and drop, scrolling). The browser is how Claude sees the UI it builds, so this must pass. A development run never uses your real home folder: if its state doesn't load, it says why on stderr and Home is a `home` folder inside the data dir (running `claude` in your home folder sets off macOS's folder-access prompts). `YH_THREADS_PROBE=<steps.json>` runs the thread tools at launch (`[{"as": "<thread id>", "tool": "list_threads", "args": {}}]`, `as` picks the calling thread, whose project decides what it reaches) and prints each result and the selection at the end to stderr; pass `CLAUDE_CONFIG_DIR=<scratch>` for the Claude Code sessions, never your real `~/.claude`. `YH_STATE_EXPORT=<file.yhstate>` exports the whole state at launch (`YH_STATE_EXPORT_SIGNINS=1` with the browser's cookies) and prints its manifest to stderr; `YH_STATE_IMPORT=<file.yhstate>` imports one at launch without asking, scratch states only (Home is pointed at the scratch `home` folder; other projects keep the file's paths, so only import files whose project folders are throwaway or missing); `YH_STATE_IMPORT_ASK=<file>` opens Import State's question for it (snapshot it with `YH_SNAPSHOT`), and `YH_STATE_IMPORT_CONFIRM=1` then says yes, keeping a copy, and restarts (without the `YH_STATE_*` variables). To reproduce someone's bug, `scripts/preset.sh` any preset, then `scripts/dev-run.sh <folder> YH_STATE_IMPORT=<their file>`; never import into your real app to look at someone else's state. Dev copies share one browser profile, so an import with sign-ins resets the browser of the file's projects for every Dev copy. `YH_IMPORT_COOKIES=<Cookies.binarycookies>` imports a Safari-format cookie file into the selected thread's project at launch: test cookie import with a synthetic file, never by reading the user's real Safari or Chrome (that prompts them for Full Disk Access or the keychain). `YH_MOCK_PULLS=<pulls.json>` serves pull requests from a file instead of `gh`/`glab` (see `Support/MockPullRequests.swift` for the shape), for a scratch workspace whose remotes point at a forge it can't reach; the file is read again when it changes, so editing it mid-run (a PR merged, one gone from the open list) shows up at the next refresh. `YH_PR_PANEL_LOG=1` prints every change in what the right sidebar's PRs tab lists (which PRs, in what order and state), for telling a flicker. `YH_UPDATE_FEED=<release.json>` reads releases from a file shaped like GitHub's `releases/latest`, or a `releases` list for several releases' notes, instead of GitHub (its disk image may be a `file://` or local `http://` URL): Dev copies only look for updates with it, and an update only installs over an app with the same bundle ID, so test the whole flow (download, Restart) with a Dev copy and a DMG of a Dev copy with a higher version. Restart reopens with the same `YH_*` variables, in the background when `YH_DATA_DIR` is set. `YH_SWITCH_PROBE=<rounds>` switches through the sidebar's threads that many rounds at launch, as clicking does, and prints to stderr each switch as it happens and a summary: go by **main thread busy** (CPU time), not wall time, which a background window inflates (it's drawn late). `YH_SWITCH_ANIMATED=0` switches without the sidebar's animation, `YH_SWITCH_PROBE_THREADS=<n>` goes round the first n threads only (the last four visited are kept made, so that's the back-and-forth case), `YH_TURNS_PER_PAGE=<n>` changes how many turns a transcript lays out. Run it on a big scratch state after changes to the thread view, and on one whose threads end in big Mermaid diagrams after changes to diagrams (they cost on every switch: make one by appending replies with three ```` ```mermaid ```` blocks of 25–40 nodes to `legacy-big`'s long threads). A row counts as in view when any part of it is, since a diagram or a long answer can be taller than the screen. For the transcript going blank: after each switch it checks for rows but none in view, a window of the app's over the main one, and nothing drawn in the conversation area (`BLANK` lines); `YH_SWITCH_PROBE_SCROLL=<points>` reads back that far in each thread before leaving (real wheel events), `YH_SWITCH_PROBE_HOLD=<ms>` stays put after each check and the probe prints the window's id, so `screencapture -x -l <id>` can take what's really on screen (drawing the window redraws every view, so it can't show a stale one), `YH_SWITCH_PROBE_SHOTS=<folder>` keeps drawings of the first blanks, `YH_BLANK_WATCH=1` checks the open thread four times a second the whole run (`YH_BLANK_SCROLL=<seconds>` scrolls it up once then, as reading back mid-turn does), and `YH_FULL_SCREEN=1` makes the window full screen at launch. Debug → Capture Transcript State (`YH_CAPTURE_TRANSCRIPT=<seconds>` at launch) writes the open transcript's scroll position, rows in view and window state to `diagnostics/` in the data folder; a transcript that finds itself blank for a second (rows, none in view) captures itself there too, once a launch, and goes to its end. `YH_NAV_PROBE=<folder>` goes between threads, a new thread, a project's Pull Requests and Memory pages and the right sidebar, wide and at the narrowest, through the sidebar's own calls, drawing the window after each step into the folder and printing PASS/FAIL: a step fails if it makes the window bigger (Memory once grew it to 4000 pt tall, and 1300 wide with memories in it: try it on `scripts/preset.sh memory` with `YH_MEMORY_SEED=200` too) or the right sidebar doesn't give back the width it took. Run it after changes to the window's layout or a page's. To see where time goes, attach Time Profiler once the probe prints its first round: `xcrun xctrace record --template 'Time Profiler' --attach <pid> --time-limit 6s` (with `DEVELOPER_DIR` set), then `xctrace export … table[@schema="time-profile"]`; `sample` alongside the probe slows the process several times over. `YH_STACK_PROBE=<prefix>` runs GitHub stacks end to end at launch through the buttons' own calls, in the first GitHub repo of the open project overview: it stacks branches `<prefix>-1…3` (make them first, one commit each), adds `<prefix>-4`, merges part then the rest, and checks a thread's PRs, printing PASS/FAIL per step (`YH_STACK_PROBE_SHOTS=<folder>` draws the window after each, `YH_STACK_PROBE_SPLIT=1` adds Claude splitting a thread's work). It merges for real: only in a sandbox repo, and point the project at the clone itself, never a folder above it. `YH_EXPAND_WORK=1` opens every finished turn's folded work. `YH_SNAPSHOT=<file.png>` (and `YH_SNAPSHOT_DELAY=<seconds>`) draws the main window into a PNG after launch, and an open sheet into `<file>-sheet.png`, for when the screen can't be captured. `YH_OPEN_BROWSER_WINDOW=1` opens the selected thread's browser in its own window. `YH_APPEARANCE=light|dark` overrides the Appearance setting without saving it. `YH_OPEN_SETTINGS=1` opens Settings. `YH_INSPECTOR_PANEL=pullRequests` (or `sideChat`, `subagents`, `browser`) opens the right sidebar on that tab. `YH_SCROLL_PROBE=<points>` scrolls the open thread up (negative: down) in trackpad-sized steps and prints how often a row on screen moved by more or less than the step, the jump count; `YH_SCROLL_PROBE=log` prints the scroll geometry instead. Run it after transcript layout changes; its step and jump counts vary a lot from run to run (earlier turns load in on the way up), so compare a few runs, and the worst jumps. `YH_FOLLOW_PROBE=<steps>` plays a long turn into the selected thread at launch (stream-json lines through the real parser, no session, 60 rows of history seeded into an empty thread): streaming text, tool calls, an answer arriving in one piece, long output, the work folding away at the end, plus a wheel scroll up halfway (it must stay put) and a jump back to the end. It prints each time the end went out of view with nobody scrolling, and PASS/FAIL (`YH_FOLLOW_PROBE_QUIT=1` quits after; about 90 s for 50 steps; keep its window uncovered, or the turn plays at a crawl). Run it at 12 steps too, and in a big window (`defaults write com.mdovhopo.yourharness.dev "NSWindow Frame main" "0 0 1728 1084 0 0 1728 1084"`, a 14" MacBook's screen; `defaults delete` it after): that's where the transcript went blank once a turn's work folded away, at 12 steps in a normal window while rows animated, and in the big one even without. `YH_BLANK_HEAL=0` leaves a transcript found blank as it is (it's still captured), so `screencapture -x -o -l <window id>` can show it. `YH_FOLLOW_PROBE_AWAY=1` ends the turn while you're in another thread and comes back after, and `YH_FOLLOW_PROBE_UNLOAD=1` also lets the thread's transcript go meanwhile. `YH_FOLLOW_LOG=1` prints every scroll report of the open transcript and whether following went on or off. Run both after changes to how the transcript scrolls; a failure can be one run in three, so run it a few times. The right sidebar's open state is saved (`showsInspector`, seeded from `state.json`), so a scratch state can open it. Memory has its own (see docs/memory.md): `YH_OPEN_MEMORY=1` (with `YH_MEMORY_TAB=memories|insights|activity|graph`), `YH_MEMORY_SEED=<n>`, `YH_MEMORY_IMPORT=<path>`, `YH_MEMORY_EXPORT=<folder>`, `YH_MEMORY_AGENT=importer|reconciler` (with `YH_MEMORY_AGENT_START=1`, `YH_MEMORY_IMPORT_SOURCES`, `YH_MEMORY_AGENT_NOTE`, `YH_MEMORY_AGENT_MODEL=haiku`), and `YH_SNAPSHOT_WINDOW=<title>` to snapshot another window, and `YH_SPOTLIGHT=<words>` opens ⌘K with them typed; `scripts/preset.sh memory <dir>` makes a project to try it on, outside this repo (inside it, Claude reads the repo's CLAUDE.md too). `YH_OPEN_USAGE=1` opens the usage view (`YH_USAGE_RANGE=week|month|quarter|halfYear|year`, `YH_USAGE_METRIC=cost`, `YH_USAGE_SPLIT=1` for a row per model, `YH_USAGE_HOVER=<days ago>` to show a day's tooltip, the pointer ignored), `YH_USAGE_PROBE=1` then moves the pointer across the chart and scrolls over it (events handed to the window, nothing on screen moves) and prints PASS/FAIL on the main thread's longest stall (under 100 ms; `YH_USAGE_PROBE_WAIT=<seconds>` before it starts, for attaching Time Profiler; run it after changes to the usage charts), and a development run prints how long reading the history and each report took; `scripts/preset.sh usage` makes a year of generated Claude Code history to point `CLAUDE_CONFIG_DIR` at (never your real `~/.claude`). `YH_SEARCH_PROBE=<words>` moves every old transcript into the database and indexes it at launch, then prints the timings and what a search across threads finds.

## Principles

- **Performance and memory are the product.** Check app footprint (`footprint $(pgrep -x YourHarness)`) after UI changes that touch the transcript. Use Debug → stress transcript.
- **Apple-quality UI.** Native controls, Liquid Glass (`glassEffect`, `.glass` button styles), SF Symbols, standard shortcuts. No web views. Draw from `Views/Theme.swift` so the window stays coherent: content sits on the `.canvas` (set once under the detail column), boxes use `.card()`, labels use `Chip`, radii come from `Theme`. Glass is for what floats above content (composer, prompts, buttons), not for transcript rows.
- **`HarnessCore` never imports SwiftUI/AppKit.** Adapters emit `AgentEvent`. The UI only consumes `AgentEvent`.
- **CLI protocols change often.** Parsers ignore unknown event types and must never crash on new fields. When the protocol changes, capture a real session, sanitize it (no local paths or user config), and add it under `Tests/HarnessCoreTests/Fixtures/`.
- **Never extract or reuse CLI credentials.** Always drive the official binary.
